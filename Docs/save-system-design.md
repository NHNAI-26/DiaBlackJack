> 프로젝트: DiaBlackJack
> 기획·통합 책임자: 이천서
> 작업 식별자: SV-00~SV-06
> 버전: v1.0
> 상태: SV-05 완료 · 무카드보상 RF 체크포인트 개정 · 실제 연결은 SV-06
> 최종 갱신: 2026-07-30

> **정식 런 카드 보상 제거 영향(2026-07-30)**
> 개정 체크포인트는 카드 보상 선택·건너뛰기가 아니라 전투 승리 골드 정산 완료를 기준으로 한다. 기존 SV-04 조정자는 현행 RW 코드와 함께 보존하며, RF-03의 무카드보상 흐름이 구현된 뒤 SV-06에서 새 승리 정산 이벤트로 교체한다.

## 1. 문서 목적

`rule.md`에 확정된 런 체크포인트 규칙을 실제 저장 파일과 이어하기 기능으로 옮기기 위한 기획 기준을 정의한다.

이 시스템의 목표는 전투를 한 프레임 단위로 복구하는 것이 아니다. 플레이어가 게임을 종료해도 마지막으로 완료한 안전한 진행 지점에서 런을 계속하고, 종료·재접속으로 후보나 상품을 다시 뽑는 악용을 막는 것이 목표다.

## 2. 기준 문서

우선순위는 다음과 같다.

1. `Docs/rule.md`의 `3.3 저장과 이어하기`
2. `Docs/game-design-document.md`의 런 체크포인트와 결정적 재현 기준
3. `Docs/stage-progression-design.md`의 런 상태 유지 규칙
4. `Docs/formal-run-flow-design.md`의 골드·상점·사건 순서
5. 이 문서의 임시 기획 결정

기준 문서와 구현이 충돌하면 저장 코드를 임의로 맞추지 않고 이천서가 규칙 변경 또는 구현 수정 방향을 결정한다.

> **Notion v0.7 영향 (2026-07-29)**
> 적 6종의 영혼·덱·능력·계약과 집행자의 라운드별 독극물 주입은 전투 중 임시 상태이므로 저장하지 않는다. 이어하기는 전투 시작 전 안전 체크포인트에서 같은 상대 프로필로 새 전투를 만든다. 골드는 3·4·6·7·9·15로 확정됐지만 실제 RF 상태 구현 후 안정 체크포인트에만 추가하며, 문서 수치만으로 저장 스키마를 선반영하지 않는다.

## 3. 현재 상태

현재 프로젝트에는 `Border.SaveLoad` 네임스페이스의 `Save`, `SaveLoadSystem`, `FileManager`가 존재한다.

- `Save`에는 실제 게임 필드가 없다.
- `SaveLoadSystem`은 하나의 `SaveData`를 JSON으로 기록하지만 런 상태와 연결돼 있지 않다.
- `FileManager`는 `Application.persistentDataPath`에 직접 덮어쓰며 임시 파일·백업·버전·손상 복구가 없다.
- `StageProgressionRuntime`은 `RunSaveFlow`를 소유하고 새 런 예약·이어하기·세션 교체·체크포인트 조정자를 실제 진행 화면에 연결한다.
- `PlayerRunState`는 영혼·일반/악마 덱·마지막 발급 ID를 검증해 새 객체로 복원할 수 있다.
- `RunRestoreFactory`는 스냅샷 전체 검증 후에만 `PlayerRunState`·`RunProgress`·상대/보상 생성기·`StageProgressionSession`을 새로 만든다.
- 상대·보상 생성기는 루트 시드와 저장된 종류별 순번을 재생해 다음 후보를 같게 만든다.
- Runtime의 새 런 생성 경로는 빈 악마 덱에서 결정적 시작 악마 2장을 제안하고 1장 확정 뒤 첫 체크포인트를 기록한다.
- 골드·상점·사건 흐름과 적 6종 지급량 3·4·6·7·9·15는 확정됐으나 실제 상태 API는 아직 미구현이다. 저장 체크포인트와의 최종 연결은 SV-06 범위다.

따라서 기존 파일의 존재를 저장 시스템 완료로 간주하지 않는다.

## 4. 플레이어 경험

### 4.1 기본 흐름

```text
메인 메뉴
├─ 새 게임
│  └─ 시작 악마 후보 고정 → 1장 선택 → 첫 체크포인트
└─ 이어하기
   └─ 최신 유효 체크포인트 복원 → 다음 콘텐츠 준비
```

- 저장 슬롯은 로컬 런 1개다.
- 저장은 자동으로만 수행한다.
- 전투 도중 수동 저장과 임의 슬롯 저장은 제공하지 않는다.
- 유효한 진행 중 체크포인트가 있을 때만 `이어하기`를 활성화한다.
- 새 게임이 진행 중 저장을 덮어쓰는 경우 확인 입력을 한 번 받는다.
- 런 승리·패배 저장은 결과 기록용이며 `이어하기` 대상으로 취급하지 않는다.

### 4.2 저장 표시

- 정상 저장은 짧은 `저장 완료` 또는 저장 아이콘으로 알린다.
- 저장 중에는 같은 체크포인트 요청을 중복 실행하지 않는다.
- 저장 실패 시 다음 콘텐츠로 넘어가지 않고 현재 안전 화면에서 재시도를 제공한다.
- 실패 원인은 사용자에게 경로·예외 원문 대신 `저장 공간 또는 파일 접근을 확인해 주세요`처럼 정제해 표시한다.

## 5. 체크포인트 규칙

### 5.1 체크포인트를 갱신하는 시점

| 체크포인트 | 저장 직전 완료 조건 | 이어하기 목적지 |
| --- | --- | --- |
| 시작 악마 선택 완료 | 후보 2장 중 1장 확정·시작 악마 덱 반영 | 첫 상대 선택 또는 첫 전투 준비 |
| 전투 스테이지 정산 완료 | 종료 전투의 승리와 골드 지급을 한 번 반영 | 다음 상점·사건 준비 |
| 상점 나가기 완료 | 모든 거래 종료·나가기 확정 | 다음 상대 선택 또는 보스 준비 |
| 사건 해결 완료 | 선택·비용·보상·결과 반영 완료 | 다음 상대 선택 또는 보스 준비 |
| 런 종료 확정 | 보스 승리·골드 결과 반영 또는 영혼 0 패배 | 결과 화면·새 게임 가능, 이어하기 불가 |

### 5.2 체크포인트를 갱신하지 않는 시점

- 전투 중
- 상대 후보를 보고 있거나 상대를 선택한 뒤 전투가 끝나기 전
- 악마 계약 후보·후속 선택 중
- 전투 승리 정산 처리 중
- 자동 카드·수동 카드 효과 선택 중
- 상점에 입장해 거래 중
- 사건 선택 또는 결과 처리 중
- 화면 전환·연출 중

위 상태에서 종료하면 마지막 완료 체크포인트로 돌아간다. 전투 손패, 카드 공개 상태, 덱 순서와 진행 중 선택은 복원하지 않는다.

### 5.3 시작 악마 후보 예약

첫 체크포인트는 시작 악마 선택 완료 뒤 생성되므로 선택 도중에는 복귀할 체크포인트가 없다. 후보 재추첨을 막기 위해 새 게임을 누른 순간 다음 정보만 가진 **런 예약**을 먼저 기록한다.

- 새 런 ID
- 루트 런 시드
- 시작 악마 후보를 재현할 시드와 생성 순번 또는 확정된 후보 키 2개

런 예약은 진행 체크포인트가 아니며 영혼·덱·스테이지 상태를 저장하지 않는다. 선택 완료 뒤 첫 체크포인트로 승격하고 예약을 제거한다. 예약 기록에 실패하면 후보 화면으로 이동하지 않는다.

### 5.4 SV-05 현행 구현 경계

현행 `RunSaveCoordinator`는 시작 악마 선택 완료, 카드 보상 선택·건너뛰기 완료, 보스 보상 뒤 승리와 영혼 0 패배를 안정 체크포인트로 조정한다. RF-03 이관 뒤에는 카드 보상 콜백 대신 승리 골드 정산 완료, 보스 즉시 승리와 영혼 0 패배를 기록해야 한다. 저장 파일 쓰기가 실패하면 같은 불변 스냅샷을 보류하고, 재시도가 성공하기 전까지 첫 전투 시작 또는 다음 스테이지 진입을 거부한다. 실패한 저장은 저장 순번과 시간을 새로 발급하지 않는다.

`RunReservationRepository`는 새 게임 진입 전에 런 ID·루트 시드·시작 악마 후보 키 2장을 `run-reservation.json`에 원자적으로 기록한다. 재접속 시 예약과 같은 시드로 세션을 다시 만들고 후보 ID·순서를 대조하므로 선택 화면 새로고침으로 재추첨할 수 없다. 첫 체크포인트 저장이 성공한 뒤에만 예약을 제거한다.

`StageProgressionRuntime`은 `RunSaveFlow`를 통해 저장 상태를 읽고, `StageTest`의 기존 IMGUI 화면은 `Continue`, 새 런 덮어쓰기 확인, 예약 재개, 백업·손상·버전 안내, 저장 실패 재시도를 제공한다. 보류 체크포인트가 있으면 일반 진행 입력을 숨기고 같은 스냅샷 재시도만 허용한다. `GameScene`은 체크포인트 소유자가 아니므로 변경하지 않았다.

상점 나가기와 사건 해결은 기획 체크포인트로 유지한다. 개정 일반전 승리 정산 저장에는 다음 콘텐츠 `Shop`을 기록하며, 실제 상점·사건 완료 체크포인트와 화면 라우팅은 HONG의 RF 경계와 통합하는 SV-06에서 마감한다. 라이터 또는 위스키를 이용한 방문은 다음 상점 가격 단계가 오른 상태로 저장해야 하므로, 상점 나가기 체크포인트에는 완료 방문 이력뿐 아니라 공통 서비스 가격 단계도 포함한다.

## 6. 저장하는 정보

| 범주 | 저장 정보 |
| --- | --- |
| 파일 | 스키마 버전, 콘텐츠 리비전, 저장 순번, 저장 시각, 런 ID |
| 진행 | 체크포인트 종류, 런 결과, 현재/다음 콘텐츠 종류, 스테이지 인덱스·ID |
| 플레이어 | 최대·현재 영혼, 현재 골드 |
| 일반 덱 | 모든 런 카드의 물리 ID, 정의 키, 무늬 |
| 악마 덱 | 모든 런 악마 카드의 물리 ID와 정의 키 |
| ID 발급 | 마지막 일반 카드 ID와 마지막 악마 카드 ID |
| 시작 선택 | 선택된 시작 악마 키와 필요 시 최초 후보 식별자 |
| 완료 이력 | 완료한 상점 방문 ID, 사건 ID와 필요한 결과 키 |
| 상점 경제 | 완료된 서비스 이용 방문 수에 해당하는 라이터·위스키 공통 가격 단계 |
| 결정성 | 루트 런 시드, 상대·보상·상점·사건 생성 순번 또는 다음 콘텐츠 재현 정보 |
| 종료 | 진행 중·승리·패배와 종료 원인 |

카드가 상점에서 제거됐더라도 마지막 발급 ID를 저장한다. 현재 덱의 최대 ID만 다시 계산하면 제거된 최고 ID가 재사용될 수 있기 때문이다.

서비스 가격 단계는 구매 횟수나 두 서비스의 개별 누적 횟수로 재계산하지 않고 RF가 제공하는 검증된 런 상태를 저장한다. 하나와 둘을 이용한 방문이 모두 한 단계만 올리는 규칙을 복원 과정에서도 그대로 유지하기 위해서다.

## 7. 저장하지 않는 정보

- 전투 중 손패와 공개·비공개 여부
- 뽑을 더미·버린 더미의 순서
- 현재 라운드 번호와 스탠드 상태
- 카드 효과·자동 효과·계약의 보류 상호작용
- 적 AI의 내부 결정·추론 캐시
- 연출 진행도, 애니메이션 시간과 임시 UI 포커스
- 적의 현재 영혼과 전투 임시 카드
- 로그 전문과 디버그 데이터
- 설정·키 바인딩·음량
- 메타 성장·영구 해금·통계

설정 저장과 런 저장은 파일 수명과 실패 정책이 다르므로 별도 시스템으로 유지한다.

## 8. 결정적 재현과 재추첨 방지

- 모든 런 콘텐츠는 하나의 루트 시드와 콘텐츠 종류별 생성 순번으로 재현 가능해야 한다.
- 이어하기는 저장 직후 다음 콘텐츠를 새 결과로 뽑지 않는다.
- 상대 후보·상점 상품·사건은 저장된 식별자 자체를 복구하거나 같은 시드·순번으로 동일하게 생성한다. 기존 RW 보상 후보 순번은 유산 저장 호환을 위해 스키마에서 즉시 제거하지 않는다.
- 구현 시점에 `System.Random`의 내부 상태를 직렬화하지 않는다.
- 기존 생성기가 상태ful 난수에 의존하면 루트 시드와 명시적 순번을 받는 결정적 생성 경계로 이관한다.
- 같은 체크포인트를 여러 번 불러도 다음 카드 ID와 후보 ID가 달라지지 않아야 한다.

## 9. 파일 안정성과 복구

### 9.1 파일 구성

프로토타입 기본안은 다음 세 파일이다.

- `run-save.json`: 최신 체크포인트
- `run-save.backup.json`: 직전 정상 체크포인트
- `run-save.tmp`: 쓰기 중 임시 파일

기존 `save.game`은 실제 런 데이터가 없는 레거시 파일로 취급한다. v1 구현에서 내용이 비어 있거나 호환 스키마가 없으면 `이어하기 없음`으로 처리하며 자동 변환을 주장하지 않는다.

### 9.2 원자적 저장

1. 메모리 상태를 불변 스냅샷으로 만든다.
2. 전체 스냅샷을 검증한다.
3. JSON을 임시 파일에 완전히 기록한다.
4. 기록한 임시 파일을 다시 읽어 역직렬화·검증한다.
5. 기존 기본 파일을 백업으로 교체한다.
6. 임시 파일을 기본 파일로 이동한다.
7. 성공한 뒤에만 저장 순번과 UI 상태를 갱신한다.

저장 도중 실패하면 기존 기본 파일을 유지한다. 부분 JSON으로 정상 저장을 덮어쓰지 않는다.

### 9.3 불러오기 복구 순서

1. 기본 파일 파싱·스키마·콘텐츠·불변식 검증
2. 기본 파일이 잘못됐으면 백업 파일 검증
3. 둘 다 잘못됐으면 이어하기 비활성화
4. 손상 파일은 즉시 덮어쓰거나 삭제하지 않고 진단 결과만 남김

백업을 사용한 경우 플레이어에게 복구 사실을 한 번 알린다.

## 10. 새 게임과 런 종료

- 진행 중 체크포인트가 있을 때 새 게임을 확정하면 새 런 예약을 성공적으로 쓴 뒤 기존 진행 저장을 교체한다.
- 새 게임 취소는 저장 상태를 바꾸지 않는다.
- 승리·패배 확정 뒤 터미널 체크포인트를 저장한다.
- 터미널 체크포인트는 `이어하기`를 활성화하지 않는다.
- 새 게임을 시작하기 전까지 터미널 결과는 유지한다.
- 메타 성장과 전적 누적은 현재 범위가 아니므로 터미널 저장에서 별도 프로필 데이터를 만들지 않는다.

## 14. 완료 조건

- 확정된 체크포인트 외 상태에서는 저장 파일이 갱신되지 않는다.
- 전투·보상·상점·사건 도중 종료하면 마지막 완료 체크포인트로 돌아간다.
- 같은 체크포인트에서 상대·보상·상품·사건 결과가 반복 로드에도 같다.
- 영혼·골드·일반/악마 덱·물리 ID·다음 발급 ID가 정확히 복원된다.
- 손상된 기본 파일에서 정상 백업으로 복구된다.
- 저장 실패가 기존 정상 파일을 파괴하지 않는다.
- 새 게임 취소·실패가 기존 진행 저장을 바꾸지 않는다.
- 런 종료 저장은 이어하기를 활성화하지 않는다.
- 저장·복원 10회 반복에서 상태 누적과 ID 충돌이 없다.
- 기존 CoreLoop·StageProgression 테스트가 모두 통과한다.
- 실제 프로세스 종료·재실행과 두 해상도 메뉴를 검증한다.
- 새 패키지·외부 에셋·오픈소스가 없거나 출처를 기록한다.
