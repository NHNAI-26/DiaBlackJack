# 테스트 전략

## 목적

빠른 반복과 신뢰 가능한 전체 회귀 검증을 분리한다. 테스트 수를 줄이는 것이 목표가
아니다. Unity 의존 작업과 표현 수치에 대한 불필요한 결합을 줄이는 것이 목표다.

수가 줄었다면 삭제·필터·컴파일 누락 여부를 확인한다.

## 검증 단계

### 반복 단계

변경한 계약을 직접 검증하는 테스트 클래스나 이름만 실행한다.

- 순수 규칙 변경: 관련 CoreLoop 또는 StageProgression 테스트
- Presentation 변경: 관련 Presenter 테스트
- MonoBehaviour 변경: 관련 Unity 결합 테스트
- 프리팹·씬·에셋 변경: 관련 에셋 계약 테스트와 필요한 수동 화면 확인
- 문서만 변경: 링크, 경로, 내용 검증

컴파일 오류가 있으면 테스트를 넓히지 않고 먼저 오류를 해결한다.

### 완료 단계

C# 동작 또는 Unity 에셋을 변경한 작업은 완료 전에 전체 EditMode 스위트를 한 번 실행한다.
실패가 있으면 이번 변경과 무관하다고 넘기지 않는다. 수정하거나, 테스트 계약이 잘못된
근거를 확인한 뒤 계약을 교정한다.

## 테스트 작성 원칙

- 상태 전이, 실패 원자성, 공개 정보 경계 같은 동작 계약을 우선한다.
- 프리팹은 필수 컴포넌트, 직렬화 참조, 정렬 관계, 유효 범위를 검증한다.
- 픽셀 좌표, 정확한 색 강도, 알파, 여백, 문구 원문은 명시된 디자인 계약일 때만 고정한다.
- 레이아웃 그룹이 제어하는 자식의 `sizeDelta`를 직접 강제하지 않는다.
- 표시 순서가 계약이 아니면 컬렉션은 순서가 아닌 동등 집합으로 비교한다.
- 카탈로그 문구를 검증할 때 동일 문자열을 테스트에 복제하지 않는다.
- 한 테스트는 하나의 행동 또는 하나의 에셋 계약을 설명한다.

## 구조적 후속 과제

`CoreLoop/`와 `StageProgression/`은 순수 C#이지만 현재 `Border` 어셈블리에 Unity 코드와
함께 묶여 있다. 그래서 비 Unity 테스트도 Editor에서 실행된다. 별도 .NET 테스트 경로를
만들려면 순수 런타임 asmdef 분리가 먼저 필요하다. 이는 참조 방향과 직렬화 타입 영향을
검토해야 하는 별도 아키텍처 작업으로 취급한다.
