## 1. 구현 전략

파일 쓰기부터 시작하지 않는다. 먼저 저장 가능한 도메인 상태와 불변식을 고정하고, 메모리 저장소로 스냅샷·복원 왕복을 검증한 뒤 실제 디스크와 Runtime·UI를 연결한다.

```text
SV-00 문서 기준
→ SV-01 순수 스냅샷·검증
→ SV-02 버전 JSON·원자 파일·백업
→ SV-03 현재 런 캡처·복원
→ SV-04 체크포인트 조정·결정성
→ SV-05 새 게임·이어하기·실패 UI
→ SV-06 RF/사건 통합·재실행 회귀·기록 마감
```

## 2. 공통 보호 범위

- CoreLoop 전투 규칙과 적 AI 공정성
- 전투 손패·덱 순서·보류 선택 비저장 원칙
- HONG의 `RunFlow`·`Shop` 내부 구현
- Shim0Hwan의 아트·레벨 환경
- 기존 카드·악마 정의 키와 물리 ID 의미
- 기존 `Try*` 실패 원자성
- Packages, 외부 에셋과 Unity 생성 프로젝트 파일

새 종속성을 추가하지 않는다. `.unity`·프리팹 편집은 UI 단계에서도 실제 필요성과 직렬화 충돌을 확인한 뒤 최소화한다.

## 3. SV-00 — 문서 기준 수립

### 목표

`rule.md`의 안정 체크포인트를 현재 저장·런 구조에 대조하고 구현 순서와 완료 증거를 확정한다.

### 작업

- 저장 시스템 기획서
- 개발 명세서
- 구현 계획서
- 진행 기록
- README·AI 활용·팀 역할·프로젝트 구조 기록

### 완료 게이트

- 체크포인트와 비저장 상태가 충돌 없이 구분된다.
- 저장 필드와 파생·임시 필드가 구분된다.
- 시작 악마 후보 예약과 재추첨 방지가 정의된다.
- 골드·상점·사건의 RF 의존성이 명시된다.
- 코드·테스트·씬·패키지·외부 에셋을 변경하지 않는다.

### 실제 완료

- `rule.md`, 전체 기획, 런·보상·정식 런 문서와 현재 `SaveLoad`·`PlayerRunState`·`RunProgress`·Runtime을 대조했다.
- 빈 `Save`와 직접 덮어쓰기를 완료된 런 저장으로 간주하지 않았다.
- SV-01~SV-06의 순서와 검증 기준을 문서화했다.

### 권장 커밋 메시지

```text
docs : 중도 종료가 선택 재추첨으로 이어지지 않게 저장 기준을 고정하다

Constraint: 전투·선택 중간 상태는 저장하지 않고 마지막 안정 체크포인트로 복귀
Rejected: 기존 빈 Save 클래스만 확장 | 버전·복구·순수 상태 경계가 불명확
Confidence: high
Scope-risk: narrow
Tested: 문서·현재 코드 정적 대조
Not-tested: 런타임 코드·Unity 실행
```

## 4. SV-01 — 순수 스냅샷과 검증

### 목표

Unity와 파일 I/O 없이 런 상태를 불변 스냅샷으로 표현하고 잘못된 저장 데이터를 거부한다.

### 주요 파일

- `StageProgression/Save/RunSaveSnapshot.cs`
- 카드·악마·플레이어·난수 스냅샷
- `RunCheckpointKind.cs`
- `RunSaveValidator.cs`
- StageProgression EditMode 테스트

### 작업

1. 스키마 1의 순수 스냅샷 타입을 추가한다.
2. 컬렉션을 방어 복사한다.
3. 카탈로그 키, 영혼·골드, 스테이지, 카드·악마 ID와 마지막 발급 ID를 검증한다.
4. 진행 중·터미널 저장을 구분한다.
5. 불안정 상태 캡처를 거부한다.
6. 아직 구현되지 않은 RF 데이터는 추측 타입으로 만들지 않는다.

### 완료 게이트

- SV01-U01~U07 통과
- StageProgression 전체 회귀 통과
- `StageProgression/Save`에 UnityEngine 참조 0건
- 저장 스냅샷이 원본 컬렉션 변경에 영향받지 않음

### 권장 커밋 제목

`feat : 런 상태가 파일 형식과 섞이지 않게 저장 스냅샷 경계를 세우다`

### 완료 기록

- 스키마 1의 최상위·플레이어·일반/악마 카드·난수 스냅샷과 안정 코드가 구현됐다.
- 생성 시 컬렉션을 방어 복사하고 검증 실패를 `RunSaveValidationError`로 반환한다.
- 카탈로그 키·무늬·영혼·골드·카드 ID·마지막 발급 ID·스테이지·체크포인트 조합을 검증한다.
- 현재 실제 상태가 있는 `StageCleared`, `RunVictory`, `RunDefeat`만 캡처하며 전투·보상 선택 중 캡처를 거부한다.
- 미구현 골드·시작 악마 선택·상점·사건 상태는 추측 객체 없이 0 또는 빈 값으로 유지했다.
- Unity MCP 대상 7/7, StageProgression 141/141, 전체 EditMode 483/483, 컴파일 오류 0건을 확인했다. 테스트 뒤에는 Test Framework 사전·사후 처리와 결과 경로 안내 3건만 남았다.

## 5. SV-02 — 버전 JSON·원자 파일·백업

### 목표

검증된 스냅샷을 버전 JSON으로 기록하고 쓰기 실패·손상 파일에서 정상 저장을 보존한다.

### 주요 파일

- `SaveLoad/RunSaveEnvelope.cs`
- `RunSaveSerializer.cs`
- `IRunSaveFileStore.cs`
- `SystemRunSaveFileStore.cs`
- `RunSaveRepository.cs`
- 저장 결과 타입과 EditMode 테스트

### 작업

1. 필드 기반 JSON DTO와 Mapper를 구현한다.
2. Enum을 안정 문자열 코드로 변환한다.
3. 기본·백업·임시 파일 이름을 한곳에서 관리한다.
4. 임시 기록·재검증·백업·교체 순서를 구현한다.
5. 각 파일 연산 실패를 주입할 수 있게 한다.
6. 기본 손상 시 백업을 읽고 둘 다 손상되면 명시적으로 실패한다.
7. 빈 레거시 `save.game`을 `NoSave`로 분류한다.

### 완료 게이트

- SV02-U01~U08 통과
- 파일 단계별 실패에서 이전 기본 저장 보존
- 영구 데이터 경로 밖 쓰기 없음
- 새 패키지 없음

### 권장 커밋 제목

`feat : 저장 실패가 마지막 정상 런을 지우지 않게 파일 교체를 보호하다`

## 6. SV-03 — 현재 런 캡처와 복원

### 목표

현재 구현된 영혼·일반/악마 덱·스테이지·후보 생성 정보를 저장하고 새 세션으로 복원한다.

### 주요 변경

- `PlayerRunState` 읽기 전용 마지막 발급 ID 투영 또는 Snapshot API
- 검증된 상태 전용 복원 Factory
- `RunProgress` 안정 상태 캡처
- `RunRestoreFactory`
- `StageProgressionSession` 재구성 Factory

### 작업

1. 현재 런 상태를 스냅샷으로 캡처한다.
2. 일반·악마 카드 정의와 물리 ID를 복원한다.
3. 제거된 최고 ID 이후 발급 번호를 보존한다.
4. 현재 경로·스테이지 ID와 인덱스를 복원한다.
5. 루트 시드·순번으로 상대·보상 후보를 재현한다.
6. 전체 새 세션 구성 성공 뒤에만 Runtime 교체 후보를 반환한다.

### 완료 게이트

- SV03-I01~I05 통과
- 저장 전후 공개 런 상태 완전 동등
- 복원 실패 시 기존 세션 무변경
- 현재 CoreLoop·StageProgression 회귀 통과

### 권장 커밋 제목

`feat : 이어하기가 기존 세션을 반쯤 덮어쓰지 않게 런을 새로 복원하다`

## 9. SV-06 — RF·사건 통합과 최종 검증

### 목표

실제 골드·상점·사건 상태를 체크포인트에 연결하고 프로세스 종료·재실행까지 검증한다.

### 선행 조건

- 시작 악마 후보 2장·1장 확정 상태와 성공 결과

- 전투 보상·골드 정산 완료 저장

- 사건 해결 완료 저장
- 보스 승리·패배 터미널 저장
- 10회 저장·종료·이어하기 반복
- 기본 손상·백업 복구 실제 파일 검증
- 전체 EditMode와 실제 앱 재실행
- 두 해상도·Console 확인
- 문서 4종과 공통 기록 마감

### 완료 게이트

- SV06-I01~I03 통과
- RF 통합 테스트와 전체 회귀 통과
